# Run lifecycle

## Purpose

Document the current deterministic health-run lifecycle.

## Core entities

### run_label

Declared in `runs/health-config*.json`, recorded verbatim inside every artifact, and treated as the stable fleet identifier that links a series of runs to the same policy.

### run_id

Generated by `HealthLoopRunner` via `_build_runtime_run_id`, timestamped, unique per execution, reflected in directory names and inside every artifact payload.

### HealthTarget metadata

The config supplies `cluster_label`, `context`, `cluster_class`, `cluster_role`, `baseline_cohort`, `watched_helm_releases`, and `watched_crd_families`. Labels and refs appear in snapshots, assessments, drilldowns, triggers, reviews, and proposals.

### ClusterSnapshot

Sanitized evidence captured via `collect_cluster_snapshot`, contains node/pod counts, control plane version, health signals, Helm releases/CRDs, and feeds both comparator and assessment logic.

### Assessment

Built by `build_health_assessment` from the snapshot, baseline policy, and persisted history. It populates `observed_signals`, `findings`, `hypotheses`, `next_evidence_to_collect`, `recommended_action`, `safety_level`, and `overall_confidence`.

### Comparison + Trigger

Triggered comparisons write comparison artifacts; their `ComparisonTriggerArtifact` documents why the comparator ran (policy eligibility, baseline drift, manual request, missing evidence regression, etc.).

### Drilldown

`DrilldownCollector` gathers warning events, non-running pods, pod descriptions, rollouts, image pull secret insights, and pattern-specific kubectl outputs. Drilldowns are deterministic.

### Review

`build_health_review` aggregates the current run's assessments, triggered comparisons/triggers, available drilldowns, and proposals into a single artifact.

### Proposal

Typed `HealthProposal` records describing suggested tuning to warning thresholds, noise filters, baseline releases/CRDs, or review ordering.

### ExternalAnalysisArtifact

Any provider invocation writes an artifact with `ExternalAnalysisArtifact` metadata so the UI's `llmStats` slice can report success/failure counts and latencies.

## Execution model

`run-health-loop` implements a deterministic sequence of stages. Every stage writes durable artifacts and emits structured logs.

### Deterministic core path

Snapshot collection, assessment, peer comparisons, drilldown collection, review assembly, and proposal generation form the mandatory harvest-compare-review loop. All logic is deterministic.

Assessment logic produces explicit `Signal`, `Finding`, `Hypothesis`, `NextCheck`, and `RecommendedAction` objects without calling any external reasoning engine.

### Optional provider-assisted branches

External analysis adapters (LLM or other tools) are an opt-in branch. They only run when the config enables adapters and a manual request explicitly names the target.

No provider output is injected into the default `Assessment`; the health loop persists each `ExternalAnalysisArtifact` separately.

**Provider output remains advisory** and does not alter the deterministic assessment.

### Review enrichment

Operators can enable `external_analysis.review_enrichment` to request an advisory review after the deterministic review is created. The artifact records `summary`, `triageOrder`, `topConcerns`, `evidenceGaps`, `nextChecks`, and `focusNotes`.

Review-enrichment artifacts are separate from the deterministic review and do not influence proposal generation.

## Stage-by-stage lifecycle

1. **Invocation & scheduling** — scheduler or operator starts `run-health-loop`. Lock file guards overlaps.
2. **Collection** — sanitize snapshots per target, write to `runs/health/snapshots`.
3. **Health assessment** — deterministic `build_health_assessment` runs for every target that opted into monitoring.
4. **Comparison triggers** — policy-driven comparisons only occur when peer mappings or manual triggers fire.
5. **Drilldown collection** — deterministic `DrilldownCollector` gathers kubectl evidence for triggered targets.
6. **Optional provider-assisted analysis** — adapters run only when manually requested.
7. **Review creation** — `build_health_review` aggregates results.
8. **Proposal generation** — deterministic proposals derived from the review.
9. **Notifications & UI index** — rebuild `runs/health/ui-index.json`.
10. **Completion** — history updated, `collection_status` annotated.

## Assessment logic

- **Inputs:** ClusterSnapshot, HealthTarget metadata, HealthHistoryEntry, baseline policy, warning-event threshold, ImagePullSecretInsight.
- **Deterministic pieces:** telemetry gaps, version drifts, node/pod counts, warning-event patterns, baseline violations, regressions.
- **LLM/provider output:** none inside `build_health_assessment`. LLMs only participate via explicit manual requests.

## Drilldown construction

- **Triggering:** health regressions, crashloop/image pull events, warning thresholds, job failures, manual requests, or pattern-specific flags.
- **Inventoried evidence:** warning events, non-running pods, pod descriptions, rollout status, image-pull-secret insights, pattern-specific kubectl digest output.
- The collector never depends on LLMs.

## Proposal generation

- Derived from the review's selected drilldowns, trigger details, and quality summary.
- Allowed changes: warning thresholds, noise filters, baseline releases/CRDs, drilldown ranking.
- **Forbidden proposals:** arbitrary Kubernetes manifests, raw configuration snippets outside allowed targets, live cluster mutations.

## Autonomous operations: allowed vs forbidden

### Allowed (observation-only)

- Evidence collection (only reads from Kubernetes)
- Comparisons/triggers that decide whether peer comparisons should run
- Drilldown collection (only writes structured evidence)
- Optional provider-assisted analysis that produces artifacts
- Proposal drafting and notification generation

### Forbidden (requires operator approval)

- Any live cluster mutation
- Auto-applying proposals
- Changing policy, baseline, or safety config without filing/approving a proposal
